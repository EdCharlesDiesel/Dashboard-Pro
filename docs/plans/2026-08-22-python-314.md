# Python 3.14 for the containers — and one Python across the project

**Goal:** Move the running containers from Python 3.11 to 3.14, bump the five
packages that block it, and prove nothing broke — with every one of the 56 pages
exercised before and after, not just the 5 in the current smoke slice.

**Architecture:** The code is already 3.14-clean; this is a *packaging* change.
The Dockerfile base image and five pins in `requirements.txt` move, and the
verification burden moves with them: the full suite runs **inside the container**
rather than only in the local venv, because the venv and the container have never
run the same stack and the local venv cannot prove anything about Linux wheels.

**Tech Stack:** Python 3.14, Docker Compose, pytest, Streamlit AppTest.

**Spec:** The owner's request, 2026-08-22: "update to the latest python don't
break anything rerun everything and test every page", referencing
<https://docs.python.org/3/whatsnew/3.14.html>.

## Global Constraints

- **Never commit.** The owner reviews and commits.
- `VERSION` reads **1.10.32**, so this plan takes **1.10.33**.
- Branch `DEV-04/Python-Update-version-3.14`.
- **Do not reinstall or "fix" the local `.venv`.** It is knowingly divergent and
  is being used here as *evidence*, not as a target.
- **`requirements.txt` is shared with Streamlit Community Cloud** (`runtime.txt`
  = 3.12). Every pin chosen must still install on 3.12, or that deploy breaks.
- **A page that already fails on 3.11 is not a 3.14 regression.** Baseline first,
  compare after; never attribute a pre-existing failure to the migration.

## Context

Four different Pythons are in play, and no plan document has ever said so — every
one of them claims "Tech Stack: Python 3.14", which described the venv only:

| Where | Python | Set by |
|---|---|---|
| local `.venv` | **3.14.0** | — |
| **containers (production)** | **3.11.16** | `Dockerfile:2` `python:3.11-slim` |
| GitHub Actions CI | **3.12** | `.github/workflows/build.yml:25` |
| Streamlit Community Cloud | **3.12** | `runtime.txt` |

**The language is not the risk.** Checked against the 3.14 whatsnew:

- `multiprocessing`/`ProcessPoolExecutor`: **not used anywhere** — so the
  headline change (default start method `fork` → `forkserver` on Linux) does not
  apply. This was the one with the potential to break the Linux workers silently.
- No source use of `__annotations__` (PEP 649 deferred evaluation), no
  `__trunc__`, no `create_task(name=/context=)`, no control flow in `finally`.
- Every file under `src/`, `pages/`, `deploy/` and `app.py` **compiles clean
  under 3.14**.

**The packages are the risk.** Five pins have no cp314 wheel, so 3.14 cannot even
build without moving them:

| Package | Pinned (container) | Has cp314? | Target |
|---|---|---|---|
| numpy | 1.26.4 | no | **2.4.4** |
| pandas | 2.2.3 | no | **2.3.3** |
| scipy | 1.13.1 | no | **1.18.1** |
| statsmodels | 0.14.2 | no | **0.14.6** |
| arch | 7.2.0 | no | **8.0.0** |

`psycopg2-binary`, `lxml`, `matplotlib`, `streamlit`, `MetaTrader5` and
`reportlab` already ship cp314 wheels and are left alone.

**Why pandas 2.3.3 and not 3.0.5.** The top of `requirements.txt` records that
Streamlit Community Cloud *segfaulted* on "Python 3.13 + pandas 3.0.2 + numpy
2.4.4" — a native crash, not an exception. pandas **2.3.3 is the last 2.x release
with cp314 wheels**, so it reaches 3.14 while staying on the 2.x API and avoiding
the pandas-3 half of that combo entirely. It is also the smaller production move
(2.2.3 → 2.3.3, a minor bump) versus a major one.

**What is already proven, and what is not.** The local venv runs 3.14 with numpy
2.4.4 / pandas 3.0.2 / scipy 1.17.1 / statsmodels 0.14.6 and **1804 tests pass**.
So the first-party code is clean on numpy 2.x *and* pandas 3.x, while production
is clean on pandas 2.2.3 — the code spans both APIs, which is why 2.3.3 in the
middle is low risk. It also confirms `ta`, `fredapi`, `cot_reports` and
`pandas_datareader` work on the new stack, and there is no use of any
numpy-2-removed alias (`np.float_`, `np.NaN`, …).

Three packages are **absent from the venv and therefore unproven on 3.14** —
`dukascopy-python`, `streamlit-lightweight-charts`, `anthropic`. All three are
documented as optional and self-disabling, but the container install must be
confirmed rather than assumed.

**The two known GARCH failures are explained.** `arch` is simply *not installed*
in the venv; that is the whole cause. `arch` 8.0.0 has cp314 wheels, so the
container keeps GARCH and those two tests should pass **inside the container**
even while they continue to fail in the venv.
